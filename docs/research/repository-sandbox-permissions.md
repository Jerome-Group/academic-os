# Repository sandbox permissions

Repository verification and repair need checkout writes plus one owned fixture directory, with network access disabled. The built-in Codex `:workspace` profile also permits system temporary directories. Older `sandbox_workspace_write` exclusions cannot reliably narrow an explicitly selected permission profile; OpenAI documents these as separate configuration systems. [Permissions](https://learn.chatgpt.com/docs/permissions), [Configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference).

On Codex0.166.0, the former mixed invocation allowed an isolated Java negative control to write outside its approved fixture. An explicit profile extending `:workspace`, overriding both temporary-directory tokens to read-only and admitting only the exact owned fixture restores the intended boundary. Inheriting the built-in preserves protected workspace paths. Review sessions inherit `:read-only` and receive no fixture write grant. Both profiles disable network access. Managed requirements remain applicable; a rejected profile is a prerequisite failure, never grounds for broader access.

The shared generator is `src/routine/repository-repair-permissions.ts`. Each invocation uses a fresh cryptographic profile name because Codex merges named profile tables with loaded configuration; reusing a name can retain unrelated write grants. The sandbox command and model session select their generated profile explicitly. Native controls must check owned writes, outside writes, protected paths, fixture-only Unix transport, TCP listeners and outbound connections, including when saved configuration grants broader access. Argument snapshots alone cannot establish enforcement. Verification uses synthetic private files; this policy does not grant access to module folders or provider credentials.
