# Cheatsheet releases are source-led and portable

A cheatsheet is a versioned release pair backed by a manifest and complete coverage evidence. Its
top-level TeX compiles alone; durable authoring inputs and history sit under an artifact-specific
support directory; fitting output stays in scratch. One declared authoring authority prevents an
edited release from being overwritten by stale fragments.

## Why evidence belongs beside the release

A dense sheet can look complete while dropping a question part, weakening a condition or carrying a
review credit from an older PDF. The manifest fixes the requested constraints, source authority and
exact release hashes. The coverage table fixes the status of every required part and exclusion.
Review passes only for the PDF hash that was inspected.

The released TeX remains directly beside its PDF in Personal Notes because that is the useful human
address already in use. Its support directory provides durable provenance without turning build
output into authority. Scratch paths carry reproducible intermediate runs and can be retired only
after every unique object has been classified.

## Why fitting is a measured source decision

Page count, required coverage and native font floor are simultaneous constraints. Sparse sheets use
the strongest pending sourced content; overflowing sheets compress or cut the weakest optional
content. A conflict among required content, page limit and floor returns as a concrete Owner choice.
Geometric scaling cannot settle it because scaling hides the actual type size.

## Why the route stays small

`/cheatsheet` discovers the module and selects create, revise, audit, verify or package-review. The
module's pinned `docs/40 Cheatsheet Procedure.md` owns conduct so every harness and direct module
session reads the same contract-versioned rules. The review package includes all editable authority
and is compiled in isolation, closing the missing-dependency failure that a top-level attachment can
otherwise conceal.
