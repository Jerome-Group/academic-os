# Cheatsheet preparation discovers context before authoring

A preparation request supplies intent, not a ready manifest. The router resolves that intent into
create or revise, then the pinned procedure owns the complete outcome: assessment evidence, source
selection, authoring, coverage, fitting, semantic review, verification and packaging.

The read-only `prepare` capability reuses the normative Source Map and Profile table readers. It
exposes ordered source roles, locators, missing-solution evidence, local hashes and assessment rows.
It does not assign academic authority from filenames or claim upstream freshness from local bytes.
The agent reads cited evidence and resolves substantive uncertainty before authoring. An explicit
source selection remains authoritative within the assessment constraints.

Coverage is coupled evidence: each locator belongs to its declared source and each included item
names a label present in the release TeX. Drafts may retain pending coverage; verification and
packaging require nonempty coverage with every declared required item included. These checks prove
correspondence, not mathematical correctness or coverage completeness. The pinned procedure keeps
independent mathematical and rendered-page review as semantic gates.

Repeated and interrupted runs re-observe current inputs and preserve artifact identity and unique
drafts. File existence and a successful build do not establish recovery or review.

Verification also proves included labels occur in the isolated build's auxiliary evidence; a label
inside an inactive TeX branch cannot establish release correspondence. The package supplements its
contract-required editable authority with exact cited source bytes and checksummed provenance so a
reviewer can reopen the evidence without the Module. Ordinal package paths preserve declared source
IDs as metadata while keeping them out of filesystem path construction. This extends generated
review evidence, not the universal Module structure, schema or contract version.

Package publication retains an exclusively created destination and uses the seed subsystem's
exclusive additive write primitive. A durable identity claim, checks before and after operations,
and a final check detect replaced or symlinked directories. Failure preserves partial destination
evidence and concurrent file bytes; recovery uses a fresh destination after reconciliation. Node
path-based filesystem APIs do not make identity checks and writes atomic against a hostile process
changing paths between them, so these checks do not claim that stronger guarantee.
